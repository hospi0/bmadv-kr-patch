## 2. 파일 구성 — 사실

두 디스크가 **같은 파일명 집합**을 갖고, 다음은 크기가 동일하다(내용 동일성은 미검증):
`1ST_READ.BIN`(947,300 · 양쪽 LBA 548537로 동일), `CHAR.DAT`(12,003,328),
`FACE.DAT`(39,841,792), `GRAPHIC.DAT`(1,492,992), `MAGIC.DAT`(41,197,568),
`OASOBI.DAT`(39,841,792), `PARAMETA.DAT`(2,131,968), `SCENARIO.DAT`(1,964,032),
`SOUND.DAT`(12,916,736), `0GDTEX.PVR`(131,104).

디스크별로 다른 것: `EVENT.DAT`(D1 96.8 MB / D2 105.5 MB), `MAP.DAT`(70.2 / 36.2 MB),
`PCM.DAT`(198.3 / 130.4 MB), `SYSTEM.DAT`(6,727,680 / 6,545,408), 그리고 `*.SFD` 동영상들.

`1ST_READ.BIN` 안에 12개 `.DAT` 파일명이 **16바이트 고정 슬롯 테이블**로 있다 (0x88988~0x88A27),
바로 뒤 0x88A28부터 각 파일에 대응하는 u32 값 12개(8/0x18/0x10/8/8/8/0x10/8/0x90/0x18/8/8).

## 3. 실행 파일 — 사실

`1ST_READ.BIN` 은 **스크램블되지 않은 평문 SH-4 코드**다.
근거: 0x0000 부터 `09 00`(SH-4 `nop`)이 반복되고, 0x30/0x70에 평문 ASCII
`Lib Handle Start` / `Lib Handle End` 가 있다.

**DC BIOS 폰트 ROM(0x8C0000B4 벡터)을 참조하지 않는다** — 해당 리터럴 0건.
→ 글리프는 게임 데이터가 공급한다. (후보 단계: 아직 실제 공급 블록 미확정)

## 4. 컨테이너 `CMP2` — 사실 (구조 검산 통과)

모든 `.DAT` 는 같은 컨테이너다.

```
0x00  char[4] "CMP2"
0x04  u32     0x08000040   (전 파일 동일, 의미 미확정)
0x08  u32     N            엔트리 수
0x0C  u32[2N] v[2i]   = 직전 구획의 섹터 크기
              v[2i+1] = 엔트리 i 의 시작 섹터
```

섹터 = 2048 B. 엔트리 i 는 섹터 `[start_i, start_{i+1})`.
검산: `start_0 == v[0]`(헤더 섹터 수) 이고 누적합이 파일 섹터 수와 정확히 일치한다.
5개 파일 전부 통과 → `tools/cmp2.py`

| 파일 | 엔트리 수 | 헤더 섹터 | 총 섹터 |
|------|-----------|-----------|---------|
| SCENARIO.DAT | 562 | 3 | 959 |
| SYSTEM.DAT | 10 | 1 | 3285 |
| EVENT.DAT | 351 | 2 | 47289 |
| GRAPHIC.DAT | 20 | 1 | 729 |
| PARAMETA.DAT | 20 | 1 | 1041 |

미사용 엔트리는 `11 11 11 …` 로 채운 1섹터 더미다.

## 5. 하위 컨테이너 — 후보

- `PAC ` : `magic, u32 0x10000000, u32 N, u32 total, (0x10 예약), u32 off[N] @0x20`.
  **오프셋 기준은 0x20** (검산: `0x20+off[0]` 위치에 다음 매직이 있고 `0x20+total ≤ 엔트리 길이`).
- `SCL ` : `magic, 0x10000000, {10 2x 0F 28}, 0, u32 0x10, u32 0x4C0, …` 이후 0x1000 간격 오프셋 표.
- `PVX ` : `magic, 0x11000000, …, u32 0x10, u32 0x80, u32 0x0C`, 0x70부터 8바이트 레코드
  (관측: `(0x28,0x18,0,0) (0x50,0x18,0,0) (0x28,0x18,0,0x18) …` — 스프라이트 사각형 표로 보임).

셋 다 **실제 읽기 코드 미확인**. 확정 전에는 수정 대상으로 삼지 않는다.

## 6. 텍스트 저장 — 사실

**텍스트는 u16 LE 워드 스트림으로 저장된다(디스크 상에서 SJIS 2바이트가 뒤집혀 보인다).**
워드 `w >= 0x8140` 이면 SJIS 문자(빅엔디언 2바이트로 되돌려 cp932 해석),
작은 값은 제어 토큰이다. → `tools/swap16_scan.py`

확인 예 (`SCENARIO.DAT`):
- 0x0000205E `　１章　`, 0x00002070 `　２章　` … `１２章`
- 0x00006834 `キツネに注意！！`, 0x00006A68 `丁寧に洗ってある浴槽だ！`
- 0x000070FC `（何だか、体中が痛い・・）`

제어 토큰 관측(후보): 문장 끝에 `18 00 17 00 0A 00 11 00 01 00` 패턴이 반복되고,
그 뒤 `1A 00 01 00 00 00 <id> 00 00 00 00 00 15 00 <len> 00` 형태의 헤더가 다음 문장을 연다.
`15 00` 뒤 값이 **문장 길이(문자 수)** 로 보인다 — 0x8710의 `18` = 18자 문자열과 일치.

### 초기 분량 (하한, 전수 아님)
naive swap16 스캔 기준 `SCENARIO.DAT` = **17,695 런 / 192,841 SJIS 문자**.
그래픽 노이즈가 섞이지 않은 파일이라 이 값은 실제 대사량에 가깝다고 본다(후보).
`EVENT.DAT`(96.8 MB)는 같은 스캔에서 320만 문자가 나오지만 대부분 그래픽 오탐이므로
**분량 미확정**. 별도 파서 필요.

## 7. `PARAMETA.DAT` — 사실

엔트리 중 일부가 **평문 ASCII 라벨로 시작**한다.

| # | 라벨 | 크기 |
|---|------|------|
| 6 | `Shop Buy List   ` | 2,048 |
| 7 | `LvUp Auto Se…` | 8,192 |
| 9 | `Armor Item Data ` | 14,336 |
| 15,16,17 | `Status Data     ` | 6,144 ×3 |

이름은 **고정폭 필드에 swap16 SJIS**로 들어 있고 남는 칸은 `0x8140`(전각 공백)으로 채운다.
확인 예: 엔트리 15 오프셋 0x1C 에 `アベル` + 전각공백 → 주인공 이름.
→ 아이템·인물 이름은 **고정 필드 예산** 문제다([[feedback_name_field_not_string_length]] 적용 대상).

### 외부 공용 도구

**세가 공식 CMP RLE 코덱** = `C:\claude\utils\sega-cmp\` (새턴 범용 등록, 프로젝트 밖).

## 10. 텍스트 렌더 경로 — 세이브스테이트로 확정 (2026-08-17)

입력: Flycast RZIP 스테이트 4개(`my files/1.state`+`1.png`, `2.state1`+`2.png` = **대사 한 줄만 다른 대조군**).
해제는 GDM 프로젝트 `tools/rzip.py` 재사용. 해제 크기 36,306,760 B.

### 10.1 스테이트 좌표 — 사실

`1ST_READ.BIN` 947,300 B 중 **946,968 B(99.96%) 일치**하는 앵커로 확정.

| 블록 | 스테이트 오프셋 |
|---|---|
| 메인 RAM 시작 (= 0x8C000000) | **0xABA43F** |
| 1ST_READ.BIN 적재 (0x8C010000) | 0xACA43F |
| RAM 끝 (16MB) | 0x1ABA43F |

⚠️ **0xABA43F 는 4로 나눈 나머지가 3이다.** 32비트 값을 읽을 때 워드 정렬 위상이 3이므로,
0 기준으로 4바이트씩 훑으면 전부 어긋난다. 처음에 이걸 놓쳐 TA 파싱이 통째로 실패했다.

RAM 뒤 7.9MB 는 두 스테이트 모두 **전부 0, 차분도 0** → VRAM 아님.

### 10.2 대조군 차분 — 사실

전체 다른 바이트 72,109개. 큰 덩어리 3개(0x99000·0xA3800·0xB5000)는 값이 0xE7 에 52% 몰린
**음성 데이터**. 그래픽 성질의 차분은 **0x0080B3F4~0x0080C1D5 (3,554 B)** 하나뿐이었다.

문자열 위치(현재 표시 중인 대사만 들어 있는 버퍼):

| 위치 | 성격 |
|---|---|
| RAM **0x8C247CF6** | **현재 대사 스테이징 버퍼** — 표시 중인 줄만 있다(스테이트마다 다름) |
| RAM 0x8C6E42A6 / 0x8C6E42BC | 적재된 `SCENARIO.DAT` 스크립트 버퍼(두 스테이트 모두 동일) |
| RAM 0x8CF38324 / 0x8CFB53D6 | **TA 디스플레이 리스트, 더블버퍼**(2,158 B 씩 차분) |

### 10.3 ★★렌더는 비트맵이 아니라 «텍스처 사각형»이다 — 사실

디스플레이 리스트를 파싱해 확정(`tools/ta_parse.py`). 32바이트 TA 파라미터
(`[PCW][x f32][y f32][z f32][u f32][v f32][base][offset]`).

`2.png`(`（何だか、体中が痛い・・）`, 13자)의 폴리곤:

```
x[ 48.. 76] y[168..182]  tex=0x576800 4BPP_PAL twiddled  u[0..0.4375]   v[0..0.2188]
x[ 76..104] y[168..182]  tex=0x576800                    u[0..0.4375]   v[0.25..0.4688]
...
x[272..300] y[168..182]  tex=0x577000 4BPP_PAL twiddled  u[0..0.875]    v[0..0.4375]
x[356..384] y[168..182]  tex=0x577200
x[384..412] y[168..182]  tex=0x577400
```

- **글자 사각형 = 28 × 14, advance 28.** x=48 에서 28씩 13개 → 13자와 정확히 일치.
- 세로 14 = 렌더 공간이 **640×240**(화면에서 2배 확대)이라는 뜻. 스크린샷 실측 글자 높이
  26px(원본 480 기준)과 맞는다.
- 텍스처 크기는 UV 로 역산: `0.4375×64 = 28`, `0.2188×64 = 14` → **64×64 에 28×14 글리프 8개**
  (32×16 칸). `0.875×32 = 28`, `0.4375×32 = 14` → **32×32 에 글리프 2개**.
  64×64 4bpp = 0x800 B, 32×32 4bpp = 0x200 B — 관측된 주소 간격(0x576800→0x577000→0x577200→0x577400)과 일치.

### 10.4 ★폰트는 «동적 글리프 캐시»다 — 사실

- 글리프 텍스처는 **대사가 바뀌면 같이 바뀐다**(위 3,554 B 차분의 정체).
- 그 구간을 스테이트에서 특정: **0x0080AC00 ~ 0x0080BC00** 에서 4bpp 니블 최대값이 **정확히 3**
  (그 앞뒤는 15). 화면 계조가 4단계인 것과 일치 → 이 구간이 VRAM 의 글리프 캐시다.
- 스크린샷 실측: 잉크 밝기가 `0 / 74 / 156 / 221` **4단계뿐**(최근접 확대라 원본 값 그대로).

### 10.5 이 발견이 뒤집은 것

앞선 「폰트 없음」 결론들은 전부 **전제가 틀린 검사**였다.

- 1bpp 스캔 0건 → 폰트는 1bpp 가 아니다(4계조).
- 행 단위 주기성 검사 0건 → 화면에 가는 것은 **트위들 4bpp 텍스처**라 행 개념이 없다.
- 선형 렌더 실패 → 같은 이유.

### 10.6 남은 것

1. **트위들 배열 확정** — 0x80AC00 구간을 두 비트순서·두 크기로 렌더했지만 아직 글자가
   또렷하게 안 선다(획 조각은 보인다). 텍스처 시작 오프셋 정렬을 0x40 단위로 다시 잡을 것.
2. **★원본 폰트 데이터** — 캐시는 «생성물»이다. 이걸 만드는 원본(디스크 어딘가, 압축 가능성)
   은 아직 미확정. 1/2/4/8bpp × 여러 셀 크기 주기성 검사는 `SYSTEM.DAT`·`GRAPHIC.DAT`·RAM 에서
   전부 0건 — 즉 **평문 격자 형태가 아니다**.
3. 확정 경로 = 캐시를 채우는 **쓰기 워치포인트**(VRAM 0x576800) → 소스 포인터 역추적.

| 항목 | 값 |
|---|---|
| 스테이트 위치 | **0x0080ABF0** (= TCW 주소 0x576800 → **VRAM 베이스 0x2943F0**) |
| 포맷 | 4bpp 팔레트, 트위들 |
| 트위들 비트순서 | **y-low** (y = 짝수 비트, x = 홀수 비트) |
| 텍스처 | 64×64 → 32×16 칸 8개 / 32×32 → 32×16 칸 2개 |
| 글리프 | **28 × 14**, 인덱스 0~3 |

**판정 근거(추측 아님)**: UV 로 확정한 칸 크기(32×16)와 글리프 크기(28×14) 때문에
열 28~31·행 14~15 는 반드시 패딩이다. 그 패딩의 **공백률이 정확히 1.0000** 인 조합이
`(0x0080ABF0, y-low)` 하나뿐이었다. 렌더 결과도 육안 확인:
`p1` = `（ 痛 っ ・ ・ ！ ）` 7자, `p2` = 32×32 텍스처들에 `（何` `だか` `、体` `中が`.

캐시는 **덧붙는 방식**이다 — `p2` 의 64×64 에는 직전 줄 글리프가 그대로 남아 있다.

도구: `tools/find_glyph_tex.py` (전수 탐색 + 패딩 공백률 판정), `tools/twiddle.py`.

### 10.9 다음 — 원본 폰트

지금 읽은 것은 **런타임 캐시**다. 이걸 만드는 원본은 아직 미확정.
이제 **오라클이 생겼다**: `痛` 등 28×14 4계조 비트맵을 알고 있으므로,
디스크·RAM 에서 이 픽셀을 만들어내는 데이터를 역으로 찾을 수 있다.
평문 격자 형태가 아님은 이미 확인됐으므로(1/2/4/8bpp 주기성 전부 0건) 압축을 의심한다.

### 10.10 원본 폰트 — 배제된 것들 (2026-08-17, 같은 세션)

디코드한 `痛`(28×14, 인덱스 0~3, 잉크 158px)를 **오라클**로 삼아 역검색했다.
도구: `tools/glyph_extract.py`(글자 추출·ASCII 아트), `tools/font_source_hunt.py`,
`tools/font_bitsearch.py`(비트 오프셋 무관).

**전부 0건:**

| 검색 | 범위 | 결과 |
|---|---|---|
| 2bpp 선형 (행 7·8바이트 × MSB/LSB × 값반전) | RAM 16MB, SYSTEM/GRAPHIC/PARAMETA/1ST_READ/EVENT | 0 |
| 1bpp 선형 (행 4·5바이트 × MSB/LSB) | 같음 | 0 |
| 4bpp 선형 (행 폭 28·32 × 니블순서 × 값반전) | 같음 | 0 |
| 8bpp 선형 (행 폭 28·32) | 같음 | 0 |
| **미리 트위들된 32×16 셀** (4bpp·2bpp) | 같음 | 0 |
| **비트 오프셋 무관 + stride 28~128·256·512** (두 극성) | RAM 16MB | 0 |

→ **원본 글리프 비트맵은 디스크에도 RAM에도 «그대로» 존재하지 않는다.**
   압축된 채로만 상주하고, 해제 결과가 **곧장 VRAM 캐시로** 들어간다고 본다
   (GDM 과 같은 구조 — [[reference_gdm_font_codec]] 참고).

**폰트 성질 관측(글리프 모양에서)**: 가로·세로 획은 또렷하고 `+`·`#` 중간값은
**대각선에만** 나온다 → 세로 방향 다운샘플이 아니라 **28×14 네이티브 안티에일리어싱 폰트**다.
(팔레트는 역순으로 보인다 — 인덱스 1 이 가장 밝다.)

### 10.11 다음 단서 — VRAM 접근 코드 위치

`1ST_READ.BIN` 에서 정렬된 하드웨어 리터럴을 뽑았다.

| 값 | 의미 | 파일 오프셋 (RAM 주소) |
|---|---|---|
| `0xA5000000` | VRAM 32비트 영역 | 0x09402C, **0x0C671C, 0x0C77E4, 0x0C80C8, 0x0C84AC** (0x8C0D671C…) |
| `0xA4000000` | VRAM 64비트 영역 | **0x0C8190, 0x0C8220** (0x8C0D8190, 0x8C0D8220) |

**파일 0xC6700 ~ 0xC8500 (RAM 0x8C0D6700 ~ 0x8C0D8500) 에 VRAM 접근 코드가 몰려 있다.**
글리프 캐시를 채우는 루틴이 여기 있을 가능성이 높다 → SH-4 정적 역어셈블로
소스 포인터와 코덱을 추적하는 것이 워치포인트 없이 가능한 다음 단계.

## 11. SH-4 정적 추적 (2026-08-17, 같은 세션)

### 11.1 ★★함정 — RAM 베이스는 «스테이트마다 다르다»

| 스테이트 | exe 앵커 | RAM 베이스 |
|---|---|---|
| `1.state` (p1) | 0x00AAE5FF | **0x00A9E5FF** |
| `2.state1` (p2) | 0x00AAE5FF | 0x00A9E5FF |
| `bm_s0` | 0x00ACA43F | 0x00ABA43F |
| `bm_s1` | 0x00AAEB3F | 0x00A9EB3F |

한 스테이트에서 잰 베이스를 다른 스테이트에 그대로 쓰면 **전부 어긋난다**.
이번에 실제로 겪었다 — 다른 스테이트의 베이스로 RAM 을 잘라 디스어셈블하니 전 구간이 0 으로 보였다.
**모든 스테이트마다 앵커를 다시 잰다.** (§10.2 의 RAM 주소는 이 정정 이후 값이다.)

### 11.2 SH-4 디스어셈블러

`tools/sh4dis.py` — GDM 에 편입한 `sh2dis.py`(MIT) 디코드 표 기반, 드림캐스트용 수정:
**리틀엔디언**(새턴 SH-2 는 빅엔디언), PC 상대 리터럴의 **값을 실제로 읽어 주석**,
지연 슬롯 표시. 검산: exe 선두가 정상 SH-4 코드로 해석된다.
⚠️ 읽기 전용 도구다 — 코드 생성·이동에는 쓰지 않는다.

### 11.3 텍스처 업로드 경로 — 사실

```
8c0d8156: mov.l @(56,pc),r4   ; = 0xa4000000     ← VRAM 64비트 영역
8c0d815a: mov.l @(56,pc),r3   ; = 0x8c0d7c9e     ← 복사 루틴
8c0d815e: mov r14,r5                              ← 소스 포인터
8c0d8160: jsr @r3
8c0d8162: add r12,r4          ; r4 = 0xA4000000 + r12
```

- **`0x8C0D7C9E(dst, src, len)`** = VRAM 복사기. 호출처 9곳
  (파일 0xAF464·0xAFB2C·0xB0128·0xB0330·0xB46E8·0xC6714·0xC80CC·0xC8194·0xC8224).
- **`0x8C0D3920(taddr, src, len, 24)`** = `0x11000000`(TA 텍스처 FIFO) 경유 DMA. 호출처 6곳.
- `0x8C0BF3F2` 부근은 스토어 큐 설정(`0xFF000038`/`0xFF00003C` = QACR0/1, `0xE0000000`).
- `0x8C0D6720` 은 팔레트 설정 루틴(회색 `0x007F7F7F` 등을 인덱스별로 기록).

### 11.4 글리프는 «RAM 에서 만들어져» 올라간다 — 사실

디코드한 7글자를 10종 패킹 × 6개 대상으로 재검색한 결과:

- `！`(글리프 3) → RAM **0x8C1E3050**, `）`(글리프 5) → RAM **0x8C1E4FF0**
  둘 다 **32×16 트위들 4bpp = 256 B** 형태로 정확히 일치.
- VRAM 64×64 텍스처의 **앞 512 B** 가 RAM 0x8C1D9BD0 에 있다(2048 B 전체는 없음).
- 두 위치 모두 **주변이 0 인 고립된 256 B 섬** → 폰트 표가 아니라 **작업 버퍼**다.
- RAM 16 MB 전수 스캔(`tools/scan_glyph_pool.py`, 패딩 열 28~31·행 14~15 가 0 인 256 B 블록)
  결과 **단 3개** → **폰트는 RAM 에 통째로 상주하지 않는다.**

### 11.5 현재 결론

원본 폰트는 **압축·부호화된 채로만 존재**하고, 글리프는 필요할 때 하나씩
256 B 트위들 블록으로 만들어져 VRAM 캐시에 올라간다.

**다음 단계**: `0x8C0D7C9E` 의 9개 호출처를 위로 거슬러 올라가 소스 포인터가
0x8C1D9xxx/0x8C1E5xxx 대역을 가리키는 경로를 찾는다 → 그 위가 래스터라이저/해제기다.
(RAM 0x8C1C1C00 에 `EVENT.DAT` 가 적재돼 있다 — 글리프 버퍼는 그 뒤쪽 대역이다.)

## 12. 텍스처 디스크립터 · 글리프 인덱스 (2026-08-17)

### 12.1 텍스처 디스크립터 표 — 사실

전역 배열, 엔트리 **0x44 바이트**. p1 첫 엔트리는 RAM `0x8C0F76C8`.

| 오프셋 | 내용 | p1 예 |
|---|---|---|
| +0x00 | 타입 | 0x00000012 |
| +0x04 | **TCW** | 280AEC00 |
| +0x0C | **소스 RAM 포인터** | 8C1D8F90 |
| +0x18 | TCW 포맷 베이스 | 28000000 |
| +0x1C / +0x20 | width / height | 0x20 / 0x20 |
| +0x24 | 크기 | 0x200 |
| +0x2C | **VRAM 주소** | 0x00576000 |

교차 검증: 네 엔트리의 소스 포인터가 `8C1D8F90 / 8C1E0FB0 / 8C1E2FD0 / **8C1E4FF0**` 이고,
마지막은 §11.4 에서 **독립적으로** 찾은 `）` 글리프 위치와 정확히 일치한다.
글리프 텍스처는 **32×32(0x200 B)에 32×16 글리프 2개**이고 VRAM 0x576000 부터 0x200 간격.
(§10.8 에서 64×64 로 디코드한 것은 모튼 순서상 32×32 넷이 연속인 것과 같아 결과가 일치했다.)

### 12.2 ★★글리프 인덱스 표 — 사실

RAM **0x8C1D5018** = 글자 수(p1 7 / p2 13), **0x8C1D501C** 부터 글자마다 u16 **글리프 번호**.
`0x8C00EB00` 의 텍스트 컨텍스트가 이 배열의 커서를 들고 있다.

| 글자 | SJIS | 인덱스 | 글자 | SJIS | 인덱스 |
|---|---|---|---|---|---|
| `、` | 8141 | 1 | `い` | 82A2 | 226 |
| `・` | 8145 | 5 | `か` | 82A9 | 233 |
| `！` | 8149 | 9 | `が` | 82AA | 234 |
| `（` | 8169 | 41 | `だ` | 82BE | 254 |
| `）` | 816A | 42 | `何` | 89BD | 798 |
| `っ` | 82C1 | 257 | `体` | 91CC | 2861 |
| `痛` | 92C9 | **3114** | `中` | 9286 | 3047 |

- **SJIS 가 아니라 조밀한 순차 번호다.** 구1(기호)은 `코드 − 0x8140` 과 정확히 일치(5건).
- 구4 이상은 **JIS 순차 색인 − 59** 로 맞는다(い·か·が·だ 4건 모두 차이 59).
  → 폰트는 JIS 순서를 따르되 앞쪽에서 59자를 건너뛴 조밀 표다.
- `痛` = 3114 가 두 스테이트에서 동일 → 정적 사상이다.

### 12.3 원본 폰트 — 여전히 미확정 (배제 목록 확장)

`痛`(값1 137px·값2 13px·값3 8px) 등 글리프 10개를 질의로 **디스크 12개 파일 전부 + RAM 16MB** 를
다음 표현으로 검색해 **전부 0건**:

2bpp 선형(행 7·8B × MSB/LSB) / 4bpp 선형(폭 28·32 × 니블순서 × 값반전) / 8bpp 선형 /
**미리 트위들된 32×16**(4bpp·2bpp) / 1bpp 마스크 / **비트오프셋·stride 무관**(28~128·256·512, 두 극성) /
**비트플레인 2bpp**(plane0/1 × 값사상 3종 × MSB/LSB) / **값 선택 마스크**(only1·only2·only3·1or2·1or3·2or3) /
**가로 볼드 해제**(`G|(G>>1)` 역산 — 검산 자체가 실패해 이 가설은 기각).

- **단조 증가 오프셋 표 없음**(u16/u32 × LE/BE, 길이 800 이상) → 가변길이 압축 표가 아니라
  **고정 크기 글리프**이거나, 표까지 압축돼 있다.
- 글리프 값 분포는 «본체 = 값 1, 대각선 가장자리만 값 2·3» → 가장자리는 런타임 생성일 수 있으나
  본체 마스크(only1)도 어디에도 없다.

**남은 경로**: 텍스트 모듈(RAM 0x8C04C000~0x8C060000, 전역은 0x8C1D4000~0x8C1D6000 대역)에서
글리프 인덱스 → 픽셀을 만드는 함수를 역어셈블로 특정하는 것. 인덱스 표를 참조하는 리터럴은
`0x8C05D5A0`·`0x8C05E014` 두 곳뿐이다.

## 13. ★★★폰트 원천 = 드림캐스트 «부트롬 폰트» (2026-08-17)

도구: [japanese-cake/jc-bootrom-font](https://github.com/japanese-cake/jc-bootrom-font)
(커밋 `fbda1b0`) 의 `font-unpacker.py` 배치 상수를 우리 `tools/bios_font.py` 로 이식.
BIOS: `D:\hospi\RetroArch\system\dc\dc_boot.bin` (2 MB), **폰트 ID `FNT90427`**.

### 13.1 부트롬 폰트 배치 (jc-bootrom-font 기준)

```
0x00100018  폰트 ID 8 B
0x00100020  데이터 시작
   ascii       96 × 36 B (12×24)
   iso-8859-1  96 × 36 B
   jis-x-0201  96 × 36 B
   jis-x-0208  7056 × 72 B (24×24 1bpp)   ← 한자·가나
   sega-gaij   22 × 72 B
   vmu-icon    129 × 128 B (32×32)
```
JIS0208 국소 인덱스 = `row*94 + col`, row 0~6 → JIS 구 0x21~0x27, row 7~ → 구 0x30 부터.

### 13.2 근거

1. **모양 일치** — `痛`(SJIS 0x92C9 → BIOS 국소 인덱스 2580, ROM 0x12FE40)을 24×24 로 뽑아
   28×14 로 축소하니 실기 캐시 글리프와 **구조가 그대로 겹친다**: 疒 부수의 윗점·긴 가로획·
   세로획·왼쪽 사선들, 오른쪽 用 상자의 가로획 3개 위치까지 동일.
   스케일 파라미터 스윕 최고 일치 **316/392 (80.6%)** (`sx=0.923, sy=1.714, 세로 OR`).
   남는 차이는 캐시 쪽 획이 굵기 때문(잉크 158 vs 130).
2. **디스크·RAM 어디에도 폰트가 없다** — §10.10·§11.4·§12.3 의 전수 검색 결과와 정확히 일치한다.
   부트롬 폰트 원본 72 B 글리프와 JIS0208 앞 4 KB 덩어리를 12개 파일 + RAM 에서 찾아도 **0건**
   (즉 게임이 복사해 온 것도 아니다).
3. **폰트 ROM 베이스가 RAM 에 상주** — `0xA0100000` 이 **RAM 0x8C0000A4** 와 `0x8C0011D4` 에 있다.
4. 게임은 BIOS 시스템콜을 쓴다 — `0x8C0000B0`(SYSINFO) 스텁 3개를 `0x8C0B8454/8468/847C` 에서 확인
   (r7 = 0/2/3). 다만 **FONTROM 벡터 `0x8C0000B4` 리터럴은 0건** — 폰트 ROM 은 주소로 직접 읽는 것으로 보인다(미확정).

⚠️ 판정: **강한 정황**이다. 실제 읽기 명령까지는 아직 추적하지 못했다.

### 13.3 게임 내부 글리프 번호 ↔ BIOS 인덱스

둘은 다른 체계다.

| 글자 | SJIS | 게임 인덱스 | BIOS 국소 인덱스 |
|---|---|---|---|
| 何 | 89BD | 798 | 876 |
| 体 | 91CC | 2861 | 2395 |
| 中 | 9286 | 3047 | 2513 |
| 痛 | 92C9 | 3114 | 2580 |

게임 쪽은 **리드 바이트당 256칸** 격자다(후보 식, 4건 일치):
`eff(T) = T − 0x40 − (T > 0x7F)`, 리드 ≥ 0x88 → `index = (L − 0x88)×256 + eff(T) + 418`.
리드 0x81~0x87(기호·가나)은 0~417 에 조밀 배치(0x81 → `eff(T)`, 0x82 → `eff(T)+129`, 각각 5·4건 일치).
BIOS 쪽은 구당 94칸이므로 게임은 별도 변환을 거친다.

### 13.4 한글화에 대한 함의 (중요)

- **디스크에 폰트가 없으므로 「폰트 파일을 한글로 교체」하는 경로는 존재하지 않는다.**
- 대신 파이프라인이 우리에게 유리하다: 래스터라이저가 **24×24 1bpp → 28×14 4계조** 축소·안티에일리어싱을
  이미 해 준다. 즉 **24×24 1bpp 한글 글리프**만 공급하면 렌더·캐시·업로드는 전부 기존 경로가 처리한다.
- 필요한 개입 = 글리프 페치 지점을 부트롬 대신 **우리 테이블**로 돌리는 코드 훅 + 디스크에 한글 글리프 테이블 추가.
  ⚠️ 사용자 BIOS 는 절대 수정 대상이 아니다.
- 다음 판정 실험: `0xA0100020` 을 읽는 명령을 특정한다(리터럴이 없으므로 `0x8C0000A4` 를
  읽어 쓰는 코드 또는 계산 경로를 추적).

도구: `tools/bios_font.py` (BIOS 글리프 추출·ASCII 아트).

### 13.6 현재 판정

> **부트롬 폰트가 가장 유력한 가설이다.** 모양이 맞고, 계조가 커버리지와 맞고,
> 디스크 두 트랙·46파일·RAM 16MB 어디에도 폰트가 없다는 사실과 정합적이다.
> **그러나 게임이 폰트 ROM 을 읽는 경로를 아직 하나도 짚지 못했다** —
> 시스템콜도 안 쓰고, 주소 리터럴도 없고, 살아 있는 포인터도 없다.
> 이 구멍을 메우기 전에는 «확정»으로 올리지 않는다.

**다음 판정 실험(워치포인트 없이)**: RAM 스냅샷 위에서 SH-4 인터프리터로
글리프 생성 경로를 실제로 실행해 어떤 주소를 읽는지 관측한다. 출발점은 확보돼 있다 —
텍스트 줄 레코드 풀 `0x8C1D5018`, 텍스처 디스크립터(소스 포인터 `0x8C1D8F90` 계열),

(캐시 실측 36과 일치)이 나와 유망해 보였으나, **렌더해 보니 규칙적 디더 패턴이었다 — 오탐.**

### 16.4 남은 방법은 하나

정적 패턴 검색은 이제 정말 소진됐다(값·패턴·포맷·컨테이너·출처 전부 훑었다).
**남은 것은 게임 코드를 실제로 실행해 «어느 주소를 읽는지» 관측하는 것뿐이다.**

- 재료는 다 있다: 정확한 RAM 스냅샷(ram_p1/p2), `tools/sh4dis.py` 의 디코드 표,
  진입점 후보(텍스트 줄 레코드 풀 `0x8C1D5018`, 텍스처 디스크립터 표 `0x8C0F7464` 엔트리 0x44 B,
  소스 버퍼 `0x8C1D8F90` 계열, VRAM 복사기 `0x8C0D7C9E`).
- 방식은 GDM 에 편입한 툴셋이 같은 벽을 뚫은 것과 동일하다
  (`sh2emu.py` 로 엔진 루틴을 오프라인 실행 — `tools/third_party/new-parm-archives-tools`).

## 17. ★PyPVR 로 텍스처 해독 성공 (2026-08-17)

사용자가 준 드림캐스트 범용 도구(`C:\claude\utils\dreamcast\`, [[reference_dreamcast_tools]])의
**PyPVR** 을 `.DAT` 에 그대로 걸었더니 **텍스처가 정상으로 나왔다.**

| 파일 | 추출 텍스처 | 내용 |
|---|---|---|
| `SYSTEM.DAT` | **45장** (대부분 256×256 RGBA) | 타이틀 메뉴(`Press Start`/`New Game`/`Config`), 캐릭터 초상화, 디스크 교체 안내, 상태창 UI, VMU 아이콘, **`000.png` 에 영숫자 폰트 아틀라스** |
| `GRAPHIC.DAT` | 11장 | 전투 결과·랭크 화면(`REPORT of BATTLE`, `RANK S/A/B/C`), 게이지 |
| `PARAMETA.DAT` | 12장 | 필드 스프라이트 시트, 초상화 모음, LEVEL UP 연출 |
| `CHAR.DAT` | 164장 | 전투 캐릭터 스프라이트 시트 |

→ 산출물 시트: `my files/mfd/{sysdat_sheet,gp_sheet,char_sheet}.png`

### 17.1 이것이 뒤집은 것

§16.3 에서 「압축이 아니라 배치 문제」라고 판정했는데, PyPVR 이 그것을 **실증**했다.
내가 자작 디트위들러로 여러 세션 그린 「노이즈」는 전부 PVR 배치(트위들·VQ·팔레트 분리)였다.
**드림캐스트에서 그림이 노이즈로 보이면 자작 도구를 짜기 전에 PyPVR 부터 건다.**

### 17.2 그래도 대사 폰트는 아직 없다

- 위 4개 파일의 추출물 **232장 어디에도 수천 자 JIS 폰트 아틀라스가 없다.**
- 텍스트 모듈이 쥔 **590 KB 청크**(`SYSTEM.DAT 0x424E0~0xD2500`)만 잘라 PyPVR 에 걸면 **PVR 0건** —
  즉 그 청크는 PVR 텍스처가 아니라 «다른 형식의 원시 데이터»다(희소 2bpp, `MFD ` 헤더로 시작).

### 17.3 다음

1. 남은 큰 파일에 PyPVR: `EVENT.DAT`(96 MB)·`FACE.DAT`·`MAP.DAT`·`MAGIC.DAT`·`OASOBI.DAT`·`1ST_READ.BIN`.
2. `SYSTEM.DAT` 의 `000.png`(영숫자 폰트 아틀라스) 전체 해상도 확인 — 가나·한자가 같이 있는지.
3. 590 KB 청크는 PVR 이 아니므로, **읽는 코드**(`0x8C1D8318` 참조, 텍스트 모듈 파일 0x4D58C 부근)를
   역어셈블해 인덱싱 규칙을 확정한다.

## 18. ★★★폰트 확정 (2026-08-17)

정적 탐색이 아니라 **코드를 읽어서** 확정했다.

### 18.1 글리프 주소 계산 — `0x8C05DD1A` (exe 파일 0x04DD0A)

```
8c05dd1a: extu.w r4,r4          ; r4 = 글리프 인덱스 (u16)
8c05dd1c: mov.l @(148,pc),r3    ; r3 = 0x8C1D8318  ← 폰트 청크 포인터를 담은 전역
8c05dd1e: shll2 r4              ; ×4
8c05dd20: shll2 r4              ; ×16
8c05dd22: mov.l @r3,r0          ; r0 = 청크 베이스
8c05dd24: shll2 r4              ; ×64
8c05dd26: shll  r4              ; ×128
8c05dd28: add   r4,r0
8c05dd2a: rts
8c05dd2c: add   #16,r0          ; 반환 = 베이스 + 16 + 인덱스×128
```

### 18.2 SJIS → 글리프 인덱스 — `0x8C05DD2E`

```
0x8140 ≤ c ≤ 0x81BF :  index = (c + 0x7EC0) & 0xFFFF
0x8240 ≤ c ≤ 0x83BF :  index = (c + 0x7E40) & 0xFFFF
0x889F ≤ c ≤ 0x9872 :  index = (c + 0x7961) & 0xFFFF
그 밖               :  index = c & 0xFFFF
```
검산: `、`8141→1 · `・`8145→5 · `！`8149→9 · `（`8169→41 · `）`816A→42 ·
`い`82A2→226 · `か`82A9→233 · `が`82AA→234 · `だ`82BE→254 · `っ`82C1→257 ·
`何`89BD→798 · `体`91CC→2861 · `中`9286→3047 · `痛`92C9→3114.
**실기에서 역산한 14개 인덱스와 전부 일치.**

### 18.3 폰트 실체

| 항목 | 값 |
|---|---|
| 위치 | **`SYSTEM.DAT` 0x424E0 + 0x10** (RAM `0x8C75F800`+0x10) |
| 청크 전체 | `SYSTEM.DAT` 0x424E0 ~ 0xD2500 = **589,856 B** (RAM 에 그대로 적재) |
| 헤더 | `MFD ` + u32 0x2000, **총 16바이트만** 건너뛴다 |
| 글리프 | **128 B = 2bpp 32×16, 트위들(y-low, 16×16 블록 2개)** |
| 글리프 수 | 약 4,600 |

### 18.4 검증 — 실기 캐시 글리프와 «픽셀 값» 대조

| 글자 | 인덱스 | 값 완전일치 |
|---|---|---|
| `！` | 9 | **388/392 = 99.0%** |
| `・` | 5 | **388/392 = 99.0%** |
| `）` | 42 | 361/392 = 92.1% |
| `（` | 41 | 359/392 = 91.6% |
| `っ` | 257 | 344/392 = 87.8% |
| `痛` | 3114 | 325/392 = 82.9% |

⏳ 83~92% 인 것들은 32×16 트위들의 둘째 블록 처리와 글자별 위치 보정이 아직 안 다듬어진 탓.
폰트 확정에는 영향 없으나 **인코더를 만들기 전에 100% 왕복을 맞춰야 한다.**

### 18.5 ★왜 그렇게 오래 걸렸나 (재발 방지)

1. **결과물을 질의로 삼았다** — 실기 캐시(28×14)로 원본(32×16)을 찾으려 했다. 축소·재배치된
   산출물로는 원본을 못 찾는다. 인덱스·주소 계산은 **코드에서 읽어야** 했다.
2. **헤더 크기를 눈대중으로 0x80 으로 잡았다.** 실제는 **0x10**. 코드가 `add #16,r0` 로 말해 준다.
3. **MFD 앞부분을 「디더 패턴」으로 오판**했다. 선형 2bpp 로 그려서 그랬고, 실제는 트위들이었다.
4. 자작 트위들러의 `morton()` 이 **x ≥ 16 을 못 다뤄** 좌우가 복제됐다 — 32×16 은 16×16 블록 2개다.
